# Interrupts in Zephyr — a practical tutorial

This document is a hands-on guide to Zephyr's interrupt subsystem
written specifically as a companion to the [ZDP framework](dvfs_pm.md).
The goal is to be able to read the framework's ISR-side code without
having to guess how Zephyr routes an interrupt or what constraints
apply to an ISR.

**Reference material**
- Kernel API doc: https://docs.zephyrproject.org/latest/kernel/services/interrupts.html
- Public header: `include/zephyr/irq.h` — the API you call from
  application code.
- Kernel implementation: `kernel/irq.c` — `k_is_in_isr`, IRQ
  offloading, tracing shims.
- Cortex-M vector table generation:
  `include/zephyr/arch/arm/irq.h`, `arch/arm/core/irq_manage.c`.
- User-tracing hooks: `subsys/tracing/user/tracing_user.c`.
- PSE84 DTS: `dts/arm/infineon/edge/pse84/pse84.dtsi`,
  `pse84.cm33.dtsi`, `pse84.cm55.dtsi`.

---

## Terminology — IRQ vs. ISR

The two acronyms are used constantly and interchangeably in
conversation, but they name different things and it is worth pinning
them down before anything else.

- **IRQ — Interrupt Request.** A *signal* generated by a peripheral (or
  by software) that asks the CPU to stop what it is doing and pay
  attention. On Cortex-M an IRQ is identified by a number: an index
  into the NVIC's interrupt table. "IRQ 18" is the peripheral-side
  wire that fires; it exists whether or not anyone has written code
  to handle it.
- **ISR — Interrupt Service Routine.** The *function* that runs when
  an IRQ is accepted. An ISR is code you write (or that a driver
  writes for you); an IRQ is an event that causes an ISR to be
  invoked. Every enabled IRQ has exactly one ISR at any given time;
  the mapping is installed via `IRQ_CONNECT()` and lives in the
  vector table.
- **NVIC — Nested Vectored Interrupt Controller.** The hardware block
  inside every Cortex-M core that prioritises pending IRQs, masks
  them, and jumps to the correct ISR. "Enabling an IRQ" (`irq_enable`)
  means unmasking it at the NVIC; "handling an IRQ" means the NVIC
  dispatching to the registered ISR.
- **Vector table.** A ROM/RAM array indexed by IRQ number; each slot
  holds the address of the ISR for that IRQ. Zephyr generates this
  table at build time from all `IRQ_CONNECT()` invocations.
- **Interrupt line.** The physical or logical wire from a peripheral
  into the NVIC input. On PSE84 a single GPIO port has one interrupt
  line into the NVIC even though it exposes up to eight pins — the
  GPIO driver's ISR reads a status register to determine which pin
  fired and calls the per-pin callback.
- **Trap / exception / fault.** Broader terms. On Cortex-M the first
  16 vector-table entries are *system exceptions* (Reset, HardFault,
  SVCall, PendSV, SysTick, …). External peripheral IRQs start at
  index 16 in the vector table but are numbered from 0 in the
  Zephyr / DT API — that is why `arch_curr_irq()` returns `IPSR - 16`.

Short version: an IRQ is *why* code runs; an ISR is *what* runs.

## 1. Concepts in ten lines

- Zephyr wraps an underlying **NVIC** (on Cortex-M) into an
  architecture-neutral API defined in
  [include/zephyr/irq.h](../../../home/ubuntu/zephyrproject/zephyr/include/zephyr/irq.h).
- Two ISR flavours:
  - **Regular ISR** — Zephyr saves context, calls your function,
    then re-enters the scheduler. Full kernel API available.
  - **Direct ISR** — smallest wrapper possible; you handle
    scheduling policy. Used for latency-critical peripherals.
- An IRQ is described in Devicetree as `interrupts = <line priority>;`
  on a peripheral node.
- Every IRQ has a **priority** (lower number = higher priority) and a
  **line number** (index into the NVIC).
- ISRs run with the CPU's interrupts masked at their priority level
  and above; they may be preempted by higher-priority IRQs.
- You must never sleep or take a blocking primitive in an ISR.
- Cortex-M reads the currently active exception number from the IPSR
  register — Zephyr exposes this via `arch_curr_irq()`.

## 2. Registration APIs

### 2.1 `IRQ_CONNECT` — the normal case

Defined in [include/zephyr/irq.h](../../../home/ubuntu/zephyrproject/zephyr/include/zephyr/irq.h).

```c
IRQ_CONNECT(irq_p,        /* IRQ line number    */
            priority_p,   /* priority           */
            isr_p,        /* handler function   */
            isr_param_p,  /* cookie for handler */
            flags_p);     /* SoC-specific flags */

irq_enable(irq_p);        /* enable at the NVIC */
```

The macro registers the handler in a static vector table generated at
build time; there is no dynamic dispatch or lookup. `isr_param_p` is
passed to the handler on every invocation and is the standard way to
identify which peripheral instance fired.

Handler signature:
```c
void my_isr(const void *arg);
```

### 2.2 `IRQ_DIRECT_CONNECT` — the low-latency case

For handlers where you want to skip Zephyr's ISR prologue/epilogue
overhead:
```c
ISR_DIRECT_DECLARE(my_direct_isr)
{
    /* raw handler — you own the world */
    ISR_DIRECT_PM();          /* opt-in: notify PM subsystem */
    my_direct_isr_body();
    ISR_DIRECT_HEADER();
    return 1;                 /* 1 = request reschedule */
}

IRQ_DIRECT_CONNECT(irq_p, priority_p, my_direct_isr, flags_p);
```

Direct ISRs have restrictions: you cannot use most kernel primitives
that trigger a reschedule from inside the handler; you must call
`ISR_DIRECT_HEADER()` and optionally `ISR_DIRECT_PM()` yourself.

### 2.3 Dynamic connect (runtime)

```c
irq_connect_dynamic(irq_p, priority_p, isr_p, isr_param_p, flags_p);
```

Requires `CONFIG_DYNAMIC_INTERRUPTS=y`. Slower first invocation
because dispatch goes through a table lookup. Rarely used in
performance-sensitive code.

### 2.4 Enabling and disabling

```c
irq_enable(irq);         /* unmask at NVIC              */
irq_disable(irq);        /* mask at NVIC                */
unsigned int key = irq_lock();  /* mask all IRQs; returns cookie */
irq_unlock(key);         /* restore mask                */
```

`irq_lock/unlock` is the equivalent of Linux's `local_irq_save/restore`
— it is a **global** mask, not per-IRQ, and it is the correct primitive
to protect very short critical sections shared with an ISR.

## 3. What runs when an IRQ fires

The exact path is architecture-dependent; on Cortex-M it is:

1. **NVIC** sees the pending IRQ, checks priority against the current
   execution priority.
2. Hardware pushes the exception frame (r0-r3, r12, LR, PC, xPSR) onto
   the current stack, switches to handler mode, and loads the vector
   from the vector table.
3. Zephyr's generic ISR wrapper
   ([arch/arm/core/isr_wrapper.S](../../../home/ubuntu/zephyrproject/zephyr/arch/arm/core/isr_wrapper.S))
   saves the remaining callee-saved registers, sets up a scratch
   frame, and calls the C dispatcher.
4. The dispatcher fires the **tracing hook** `sys_trace_isr_enter()`
   (which chains through to the user hook — see §8).
5. Your handler runs (`my_isr(param)`).
6. On return, the dispatcher fires `sys_trace_isr_exit()`.
7. If a scheduler request was pending or the handler set one, control
   goes through `sys_trace_isr_exit_to_scheduler()` and Zephyr picks
   the next runnable thread.

Direct ISRs skip steps 3 and 4 — that is where the "direct" savings
come from.

## 4. Priorities and preemption

On Cortex-M the number of priority bits is a hardware property. On
PSE84 it is 3, meaning 8 priority levels (0 = highest). Configured in
DT as
[pse84.cm33.dtsi:63](../../../home/ubuntu/zephyrproject/zephyr/dts/arm/infineon/edge/pse84/pse84.cm33.dtsi):
```dts
&nvic {
    arm,num-irq-priority-bits = <3>;
};
```

Zephyr reserves the two highest hardware priorities for its own use
(kernel-critical exceptions, SysTick). Application ISRs get the
remaining six levels.

The number you pass as `priority_p` in `IRQ_CONNECT(irq_p, 4, ...)` is
a **Zephyr priority**, not the value that ends up in the NVIC's 8-bit
priority register. Two transformations happen before the value hits
hardware:

1. **Offset by the reserved count.** Zephyr priority 0 does not map
   to NVIC priority 0 — that slot is reserved. Instead:
   `nvic_index = zephyr_priority + reserved_count`, where
   `reserved_count = 2` (SVCall + PendSV / SysTick). So Zephyr
   priority 0 → NVIC index 2, and Zephyr priority 4 → NVIC index 6.
2. **Left-shift into the implemented bits.** The Cortex-M NVIC
   priority register is 8 bits wide but only the top
   `arm,num-irq-priority-bits` are wired. On PSE84 that is 3 bits, so
   valid NVIC register values are `0x00, 0x20, 0x40, 0x60, 0x80,
   0xA0, 0xC0, 0xE0`. The final write is
   `nvic_reg = nvic_index << (8 - num_priority_bits) = nvic_index << 5`.

For `IRQ_CONNECT(irq, 4, ...)` on PSE84 this means the NVIC ends up
holding `0xC0` (index 6, shifted left by 5) — the *sixth* of the eight
usable hardware priority levels, with two above it reserved for
Zephyr. `0xC0` is a numerically *higher* register value, which on
Cortex-M means a *lower* priority — everything at Zephyr priorities
0–3 will preempt it.

The offset lives in
[include/zephyr/arch/arm/irq.h](../../../home/ubuntu/zephyrproject/zephyr/include/zephyr/arch/arm/irq.h)
as `_IRQ_PRIO_OFFSET` (also called `Z_IRQ_PRIO_OFFSET`) and the shift
is done inside `NVIC_SetPriority()` from CMSIS. You never do the
arithmetic by hand — but knowing the two steps makes it obvious why
"Zephyr priority 4 on a 3-bit NVIC" is a legal, working value.

Rule of thumb: **lower number = higher priority = preempts everything
below it**.

## 5. ISR context — what is and is not allowed

Inside an ISR you may:
- read/write MMIO,
- call `k_sem_give`, `k_msgq_put(..., K_NO_WAIT)`, `k_work_submit`,
  `k_timer_start` (any operation that does not block),
- signal a thread via any lock-free means.

You may **not**:
- call `k_msleep`, `k_sem_take` with a non-zero timeout,
  `k_msgq_get` with a non-zero timeout, `k_mutex_lock`, or any other
  primitive that can suspend the calling context,
- use `printk` at high rates (the console back-end may block),
- allocate from `k_heap` unless the pool is designed for ISR use,
- use the FPU unless `CONFIG_FPU_SHARING=y` and you enter with the
  arch-specific FPU-in-ISR sequence.

To check the current context from a helper that may run either from
an ISR or from a thread:
```c
if (k_is_in_isr()) { ... } else { ... }
```

## 6. IRQ numbers and Devicetree

Every IRQ line on the SoC has a fixed number. In DT, peripherals
declare their IRQ number and priority in the `interrupts` property.

From
[dts/arm/infineon/edge/pse84/pse84.dtsi](../../../home/ubuntu/zephyrproject/zephyr/dts/arm/infineon/edge/pse84/pse84.dtsi):
```dts
scb2: serial@42800000 {
    reg = <0x42800000 0x4000>;
    interrupts = <41 4>, <40 4>;   /* two IRQ lines, both priority 4 */
    status = "disabled";
};

gpio_prt0: gpio@42810000 {
    reg = <0x42810000 0x80>;
    interrupts = <0 4>;            /* IRQ 0, priority 4 */
    gpio-controller;
    ngpios = <2>;
};
```

The Zephyr driver for the peripheral consumes these numbers via the
`DT_IRQN(node_id)` and `DT_IRQ(node_id, priority)` macros:
```c
IRQ_CONNECT(DT_IRQN(DT_NODELABEL(gpio_prt0)),
            DT_IRQ(DT_NODELABEL(gpio_prt0), priority),
            gpio_prt0_isr, DEVICE_DT_GET(DT_NODELABEL(gpio_prt0)), 0);
```

The Devicetree is therefore the single source of truth for IRQ
numbers; you should not hard-code them in application code.

## 7. Reading the current IRQ number

Cortex-M puts the currently active exception number in the low bits
of the IPSR register. IRQ 0 corresponds to IPSR value 16 (the first
16 are Cortex-M system exceptions); the arch-neutral wrapper
`arch_curr_irq()` returns the *external* IRQ number (0-based, matches
the DT `interrupts = <N ...>` value):

```c
#include <zephyr/arch/arch_interface.h>

unsigned int irqn = arch_curr_irq();   /* only valid in ISR context */
```

Used by ZDP inside `sys_trace_isr_enter_user()` to identify which
IRQ profile to update — see §8.

## 8. Tracing hooks and ZDP integration

Zephyr calls two macro-defined trace points around every ISR:

- `sys_trace_isr_enter()` — before your handler.
- `sys_trace_isr_exit()` — after your handler.

When `CONFIG_TRACING=y` and `CONFIG_TRACING_USER=y`, both hooks chain
to weakly-linked user versions defined in
[subsys/tracing/user/tracing_user.c](../../../home/ubuntu/zephyrproject/zephyr/subsys/tracing/user/tracing_user.c):
```c
void __weak sys_trace_isr_enter_user(void) {}
void __weak sys_trace_isr_exit_user(void)  {}
```

ZDP overrides them:
```c
/* Called at the entry of every ISR, before the registered handler
 * runs. Runs in interrupt context; arch_curr_irq() returns the IRQ
 * number of the interrupt being serviced. */
void sys_trace_isr_enter_user(void)
{
    zdp_irq_on_arrival(arch_curr_irq(), k_cycle_get_32());
}

/* Called at the exit of every ISR, after the handler returns and
 * before the scheduler decides whether to switch threads. Still
 * runs in interrupt context. */
void sys_trace_isr_exit_user(void)
{
    zdp_decision_maybe_request();
}
```

No source change to Zephyr, no application change to individual
`IRQ_CONNECT` call sites. Every registered IRQ is observed
automatically.

## 9. PSE84 specifics

PSE84 has **two Cortex-M cores** and each core has its own NVIC and
its own view of the SoC's IRQ table:

- **CM33** — armv8-m, secure and non-secure worlds, up to 200 MHz.
  Vector table lives in the CM33-side ROM/RAM; the two worlds share
  the NVIC but have separate SAU-controlled views of the peripherals.
- **CM55** — armv8.1-m, up to 400 MHz. Independent NVIC, separate
  vector table.

An IRQ can be routed to CM33, CM55, or (via the CPUSS routing) to
both. In practice, in the Zephyr port, each core's DTS binding
declares only the IRQs actually wired to that core:

- [pse84.cm33.dtsi](../../../home/ubuntu/zephyrproject/zephyr/dts/arm/infineon/edge/pse84/pse84.cm33.dtsi)
  declares `arm,num-irq-priority-bits = <3>` and adds CM33-only
  IRQs (e.g. `lpcomp0: interrupts = <45 4>`).
- [pse84.cm55.dtsi](../../../home/ubuntu/zephyrproject/zephyr/dts/arm/infineon/edge/pse84/pse84.cm55.dtsi)
  declares CM55-side IRQ numbers, which are *different* from the CM33
  numbers even for the same peripheral because the two cores see
  their own NVIC index. Look for entries such as
  `interrupts = <39 4>` under `smif0` — that line number is valid on
  CM55 only.

Consequences for ZDP:
- Each core runs an **independent ZDP instance**. There is no shared
  state.
- The IRQ profile for `SCB2` on CM33 (IRQ 41) and on CM55 (a different
  number) is not the same object. If both cores are involved in the
  same logical peripheral, the two profiles must be reconciled by the
  application.
- Inter-core signalling on PSE84 uses **IPC channels** (drivers
  under `drivers/mbox/mbox_ifx_cat1_ipc.c`) which surface as normal
  IRQs on each core — from ZDP's viewpoint they are ordinary IRQ
  sources with their own PJD parameters.

## 10. Worked example — CM33-NS GPIO IRQ

Enable a GPIO input on port 0, pin 1, wake a thread on falling edge.

**Devicetree (application overlay):**
```dts
&gpio_prt0 {
    status = "okay";
};

/ {
    aliases {
        drdy-gpio = &drdy;
    };

    zephyr,user {
        drdy: drdy_pin {
            gpios = <&gpio_prt0 1 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>;
        };
    };
};
```
GPIO port 0's IRQ line comes from `pse84.dtsi`: `interrupts = <0 4>`
— IRQ 0, priority 4.

**Application code:**
```c
#include <zephyr/kernel.h>
#include <zephyr/drivers/gpio.h>

static const struct gpio_dt_spec drdy =
    GPIO_DT_SPEC_GET(DT_PATH(zephyr_user), drdy_gpios);

static struct gpio_callback drdy_cb;
static K_SEM_DEFINE(drdy_sem, 0, 1);

static void drdy_isr(const struct device *dev, struct gpio_callback *cb,
                     gpio_port_pins_t pins)
{
    k_sem_give(&drdy_sem);   /* ISR-safe */
}

int drdy_init(void)
{
    gpio_pin_configure_dt(&drdy, GPIO_INPUT);
    gpio_pin_interrupt_configure_dt(&drdy, GPIO_INT_EDGE_FALLING);

    gpio_init_callback(&drdy_cb, drdy_isr, BIT(drdy.pin));
    gpio_add_callback(drdy.port, &drdy_cb);
    return 0;
}

void drdy_thread(void)
{
    drdy_init();
    while (1) {
        k_sem_take(&drdy_sem, K_FOREVER);
        /* ... handle event ... */
    }
}
```

Notes:
- The `IRQ_CONNECT()` call is inside the GPIO driver
  (`drivers/gpio/gpio_ifx_cat1.c`) — application code never touches
  the IRQ number directly.
- `k_sem_give` is safe from ISR; use it, not `k_sem_take`.
- ZDP sees this IRQ as `irqn = 0` via `arch_curr_irq()` and estimates
  its PJD parameters automatically.

## 11. Worked example — CM55 SCB2 UART IRQ

Same peripheral, but on CM55. The CM55 sees SCB2 at a different NVIC
index than CM33; the DT overlay on the CM55 side takes care of the
translation. From the application's viewpoint the code is identical:

**Devicetree (CM55 overlay):**
```dts
&scb2 {
    status = "okay";
    current-speed = <115200>;
};
```
`scb2` in `pse84.dtsi` has `interrupts = <41 4>, <40 4>` — the numbers
are re-mapped when included from `pse84.cm55.dtsi` if the CM55 wiring
differs. Consult
[pse84.cm55.dtsi](../../../home/ubuntu/zephyrproject/zephyr/dts/arm/infineon/edge/pse84/pse84.cm55.dtsi)
for the definitive per-core numbers.

**Application code:**
```c
#include <zephyr/kernel.h>
#include <zephyr/drivers/uart.h>

static const struct device *uart = DEVICE_DT_GET(DT_NODELABEL(scb2));

static void uart_cb(const struct device *dev, struct uart_event *evt,
                    void *user_data)
{
    switch (evt->type) {
    case UART_RX_RDY:
        /* handle received data — ISR context via the driver */
        break;
    default:
        break;
    }
}

int uart_init(void)
{
    uart_callback_set(uart, uart_cb, NULL);
    /* set up async RX ... */
    return 0;
}
```

Notes:
- The Infineon UART driver
  ([drivers/serial/uart_ifx_cat1.c](../../../home/ubuntu/zephyrproject/zephyr/drivers/serial/uart_ifx_cat1.c))
  registers both SCB IRQ lines via `IRQ_CONNECT` on driver init.
- On CM55, `arch_curr_irq()` returns the CM55-side number, not the
  CM33 one. ZDP treats them as different profiles — that is the
  correct behaviour because a CM55 IRQ and a CM33 IRQ are independent
  observation streams even if they originate from the same peripheral.

## 12. Worked example — BGT60TR13C radar FIFO IRQ

This is the pattern the radar driver in
[modules/bgt60tr13c/drivers/bgt60tr13c/bgt60tr13c.c](../modules/bgt60tr13c/drivers/bgt60tr13c/bgt60tr13c.c)
is being extended with, and it is a good end-to-end example because
the interrupt does *not* come from an on-chip peripheral — it comes
from an off-board sensor via a plain GPIO pin. The path is longer than
the SCB2 UART case, and every hop is visible.

### 12.1 The physical event

The BGT60TR13C has an on-chip 8192-word FIFO. When the FIFO fill
level reaches the compare reference (`SFCTL.FIFO_CREF`) written by
`api->set_fifo_limit()`, the chip drives its IRQ pin high. That pin
is wired on the kit to the PSoC's `p20.3`:

From
[apps/09_pse84_ai_m33_radar/boards/kit_pse84_ai_pse846gps2dbzc4a_m33.overlay](../apps/09_pse84_ai_m33_radar/boards/kit_pse84_ai_pse846gps2dbzc4a_m33.overlay):
```dts
bgt60tr13c_radar: bgt60tr13c@0 {
    compatible = "infineon,bgt60tr13c";
    reset-gpios = <&gpio_prt20 7 GPIO_ACTIVE_LOW>;
    irq-gpios   = <&gpio_prt20 3 GPIO_ACTIVE_HIGH>;
};
```

### 12.2 GPIO port ↔ NVIC line

`gpio_prt20` is not itself an NVIC input, but the port controller is.
From
[dts/arm/infineon/edge/pse84/pse84.dtsi](../../../home/ubuntu/zephyrproject/zephyr/dts/arm/infineon/edge/pse84/pse84.dtsi):
```dts
gpio_prt20: gpio@42810a00 {
    compatible = "infineon,gpio";
    interrupts = <18 4>;   /* NVIC IRQ 18, Zephyr priority 4 */
    ngpios = <8>;
    wakeup-source;
};
```

So the whole port (up to 8 pins) shares a single NVIC line. The
`IRQ_CONNECT()` for IRQ 18 is done once, inside the Infineon GPIO
driver (`drivers/gpio/gpio_ifx_cat1.c`) during its `POST_KERNEL`
init. The driver's ISR reads the port's interrupt-status register,
identifies which pin fired, and invokes the per-pin callback that was
registered via `gpio_add_callback()`. Application and sensor-driver
code never touch IRQ 18 directly — they register a callback for pin 3
and let the GPIO driver do the dispatch.

### 12.3 Sensor-driver side

The radar driver needs three additions (planned, not yet in tree):

1. **Config struct** — add an `irq_gpio` field alongside the existing
   `reset_gpio`:
   ```c
   struct bgt60tr13c_config {
       struct spi_dt_spec  spi;
       struct gpio_dt_spec reset_gpio;
       struct gpio_dt_spec irq_gpio;   /* new */
   };
   ```
   and populate it from DT in the instantiation macro:
   ```c
   .irq_gpio = GPIO_DT_SPEC_INST_GET_OR(inst, irq_gpios, {0}),
   ```

2. **Runtime data** — add a `struct gpio_callback` and a signalling
   primitive:
   ```c
   struct bgt60tr13c_runtime_data {
       bool                initialized;
       struct gpio_callback irq_cb;
       struct k_sem         fifo_ready;    /* given from ISR */
   };
   ```

3. **ISR + registration** — a tiny callback that only signals:
   ```c
   static void bgt60tr13c_fifo_isr(const struct device *port,
                                   struct gpio_callback *cb,
                                   gpio_port_pins_t pins)
   {
       struct bgt60tr13c_runtime_data *data =
           CONTAINER_OF(cb, struct bgt60tr13c_runtime_data, irq_cb);
       k_sem_give(&data->fifo_ready);   /* ISR-safe */
   }
   ```
   wired up during `bgt60tr13c_init()`:
   ```c
   k_sem_init(&data->fifo_ready, 0, 1);

   gpio_pin_configure_dt(&cfg->irq_gpio, GPIO_INPUT);
   gpio_pin_interrupt_configure_dt(&cfg->irq_gpio,
                                   GPIO_INT_EDGE_TO_ACTIVE);
   gpio_init_callback(&data->irq_cb, bgt60tr13c_fifo_isr,
                      BIT(cfg->irq_gpio.pin));
   gpio_add_callback(cfg->irq_gpio.port, &data->irq_cb);
   ```

4. **Public wait function** exposed on the driver API:
   ```c
   int (*wait_fifo_ready)(const struct device *dev, k_timeout_t timeout);
   ```
   implemented as:
   ```c
   static int bgt60tr13c_wait_fifo_ready(const struct device *dev,
                                         k_timeout_t timeout)
   {
       struct bgt60tr13c_runtime_data *data = dev->data;
       return k_sem_take(&data->fifo_ready, timeout);
   }
   ```

### 12.4 Application side — replace the polling loop

The current app in
[apps/09_pse84_ai_m33_radar/src/main.c](../apps/09_pse84_ai_m33_radar/src/main.c)
polls `FSTAT` every 50 µs in `wait_for_fifo()`. With the IRQ path,
that loop collapses to:

```c
for (uint32_t frame = 0; frame < NUM_FRAMES; frame++) {
    if (api->wait_fifo_ready(radar_sensor, K_MSEC(50)) < 0) {
        printk("Frame %u: IRQ timeout\n", frame);
        break;
    }
    api->get_fifo_data(radar_sensor, samples, NUM_SAMPLES);
    print_frame_stats(frame, samples, NUM_SAMPLES);
}
```

The thread now spends its time in `k_sem_take()`, which is a proper
sleep state visible to Zephyr's power-management subsystem — the SoC
can enter its idle low-power mode between frames instead of hammering
SPI.

### 12.5 Full event trace, hardware to thread

For one FIFO-ready event on this stack:

```
BGT60TR13C FIFO fill ≥ CREF
        │  (chip drives IRQ pin high)
        ▼
p20.3 rising edge
        │  (GPIO controller port 20 sets its status bit)
        ▼
NVIC IRQ 18 pending, priority 0xC0 (Zephyr prio 4)
        │  (NVIC dispatches when CPU priority allows)
        ▼
Vector table entry 16+18 → Zephyr ISR wrapper
        │  (arch/arm/core/isr_wrapper.S)
        ▼
sys_trace_isr_enter()   → ZDP records arrival on IRQ 18
        │
        ▼
gpio_ifx_cat1_isr(gpio_prt20)   /* port-level ISR from driver */
        │  reads intr_status, sees pin 3
        ▼
bgt60tr13c_fifo_isr(port, &data->irq_cb, BIT(3))
        │
        ▼
k_sem_give(&data->fifo_ready)     /* ISR-safe, non-blocking */
        │
        ▼
sys_trace_isr_exit()    → ZDP decision point (§8)
        │
        ▼
Scheduler wakes the frame-acquisition thread
        │
        ▼
k_sem_take() returns 0 in the app loop
        │
        ▼
api->get_fifo_data() runs SPI burst read (thread context)
```

Every hop is a standard Zephyr mechanism from earlier sections of
this tutorial — the interesting part is that only the top two hops
are radar-specific. Everything from IRQ 18 downwards is the same
plumbing you would see for any GPIO-driven sensor on this SoC.

### 12.6 Gotchas specific to this path

- **Port-shared IRQ.** IRQ 18 fires for any enabled input transition
  on port 20. The reset pin is on `p20.7`; make sure it is configured
  as `GPIO_OUTPUT` (interrupts disabled by default on outputs) so it
  does not add noise to the shared line.
- **Level vs. edge.** The BGT60TR13C IRQ pin is *level* while the
  FIFO stays above CREF. Configure `GPIO_INT_EDGE_TO_ACTIVE` (rising
  edge) so the ISR fires once per fill-crossing, not repeatedly while
  the chip is draining. After `get_fifo_data()` empties enough words,
  the pin will fall back low; the next fill crossing gives another
  edge.
- **Wake from deep sleep.** `gpio_prt20` in the DTS has
  `wakeup-source;`, so the FIFO IRQ can wake the CM33 from
  `SLEEP`/`DEEPSLEEP` — useful once `k_sem_take(K_FOREVER)` lets the
  system idle between frames. The SoC's PDL still needs the port
  configured as a wake source (`Cy_SysPm_SetupIoUnfreeze` and
  friends); see §13 debug tips.
- **Semaphore leak on overrun.** If the application misses a frame,
  the semaphore's max count of 1 means the next `k_sem_give()` from
  the ISR is silently dropped — which is the *desired* behaviour
  (the FIFO itself signals overflow via `FSTAT.FOF_ERR`). If you want
  a queue of frame-ready events, replace the semaphore with a
  `k_msgq` sized to your latency budget.
- **ISR keeps the SPI bus quiet.** Do not add the FIFO read into the
  ISR itself. `spi_transceive_dt()` uses a mutex on the SPI bus and
  may block; that is illegal in ISR context. The semaphore + thread
  split is not just style — it is required.

## 13. Debug tips

- **List active IRQs.** With `CONFIG_SHELL=y` and
  `CONFIG_KERNEL_SHELL=y`, use `kernel threads` to see thread state;
  use `arm irq` (custom command from `arch/arm/core/tinit.c`) to
  inspect NVIC state.
- **Trace an ISR without a debugger.** Toggle a GPIO at entry and
  exit inside the handler; watch on a scope. Sub-µs precision.
- **Priority inversions.** If a thread never runs, check the priority
  of the ISR that is supposed to unblock it — a mid-priority ISR
  spinning in a loop can starve everything below it.
- **`arch_curr_irq()` returns garbage.** You are not in an ISR. Guard
  with `k_is_in_isr()`.
- **Missed IRQs on wake-up from deep sleep.** Some SoCs (PSE84
  included) require the peripheral's interrupt-wakeup path to be
  configured separately from the NVIC — see the SoC's PDL
  `Cy_SysPm_*` functions for wake-source configuration.
- **`IRQ_CONNECT` compiled out.** The macro emits a linker section
  entry; if link-time GC is aggressive, wrap the call in
  `SYS_INIT()` or take the address of the handler somewhere so the
  linker keeps it.
