# BGT60TR13C Zephyr Driver Implementation Plan

## Official Library Analysis: `sensor-xensiv-bgt60trxx`

### Architecture

The library has a clean **platform-abstraction** design with three layers:

| Layer | Files | Purpose |
|-------|-------|---------|
| **Core** | `xensiv_bgt60trxx.c` / `.h` | Platform-independent sensor logic |
| **Platform API** | `xensiv_bgt60trxx_platform.h` | 7 functions the integrator must implement |
| **Platform Impl** | `_edge.c` (PSoC Edge) / `_mtb.c` (ModusToolbox) | Infineon HAL-based implementations |

### SPI Protocol (32-bit word format)

Every register access is a single **32-bit SPI transfer**:

```
Bit 31..25:  Register address (7 bits)
Bit 24:      Write=1 / Read=0
Bit 23..0:   Data (24 bits)
```

The word is **byte-reversed** before sending (MSB first on wire). On read, the response is byte-reversed back and masked to 24 bits.

### FIFO Burst Read (12-bit ADC samples)

FIFO reads use a special **burst mode**:
1. Send a 4-byte header: `0xFF` command byte + FIFO register address + R/W bit
2. Check GSR0 status in response for errors (overflow, SPI burst error, clock error)
3. Switch SPI to **12-bit word width** and read N samples as `uint16_t[]`

The official library **dynamically changes the SPI data width from 8-bit to 12-bit** mid-transaction via `spi_set_data_width()`. This is PSoC SCB-specific and will need careful handling in Zephyr.

### Key API Flow

```
xensiv_bgt60trxx_init()          → Detect chip (read CHIP_ID), set SPI speed mode
xensiv_bgt60trxx_config(regs[])  → SW reset + write configurator-generated register array
xensiv_bgt60trxx_set_fifo_limit()→ Set FIFO threshold for IRQ
xensiv_bgt60trxx_start_frame()   → Set FRAME_START bit in MAIN register
  ── [IRQ fires when FIFO ≥ threshold] ──
xensiv_bgt60trxx_get_fifo_data() → Burst-read ADC samples from FIFO
xensiv_bgt60trxx_start_frame(false) → FSM reset to stop
```

### Register Configuration

The `regs[]` array passed to `config()` is a pre-built list of **packed 32-bit SPI write commands** generated by Infineon's BGT60TRxx Configurator tool. Each element already encodes address + write bit + data. The library parses them back out and writes each register individually, with special handling for `SFCTL` (FIFO control).

### Platform Functions You Must Implement

| Function | Zephyr Equivalent |
|----------|-------------------|
| `platform_spi_transfer()` | `spi_transceive_dt()` |
| `platform_spi_fifo_read()` | **Problem** — needs 12-bit SPI width |
| `platform_spi_cs_set()` | GPIO-based CS (already in overlay) |
| `platform_rst_set()` | `gpio_pin_set_dt()` |
| `platform_delay()` | `k_msleep()` |
| `platform_word_reverse()` | `__builtin_bswap32()` |
| `platform_assert()` | `__ASSERT()` |

## Current State of the Driver

The module at `modules/bgt60tr13c` has the correct Zephyr module scaffolding but only implements CHIP_ID reading. Key gaps:

- No `write_reg` function
- No register configuration (configurator array)
- No FIFO read / frame control
- No IRQ handling (GPIO defined in DT binding but unused)
- Uses a custom API struct instead of Zephyr's `sensor_driver_api`
- SPI protocol doesn't match official library (read clears MSB; official uses bit 24 for R/W in a 32-bit word)

## Implementation Plan

### Phase 1: Core SPI Communication
1. **Port the SPI protocol** from official library — 32-bit word format with byte-reversal
2. Implement `write_reg()` and `read_reg()` matching the official `set_reg`/`get_reg` format
3. Verify CHIP_ID reads correctly (expect `0x000303` for BGT60TR13C — digital_id=3, rf_id=3)

### Phase 2: Sensor Init & Configuration
4. **Port hard reset** sequence (RST low 1ms, high 1ms with CS held high)
5. **Port `xensiv_bgt60trxx_init()`** — set SPI speed mode, read+validate CHIP_ID
6. **Port `xensiv_bgt60trxx_config()`** — SW reset then write configurator register array
7. Create a **default register configuration** header (from Infineon Configurator tool, or use a known-good config from an example)

### Phase 3: Frame Acquisition
8. **Implement `start_frame()` / `stop_frame()`** — MAIN register bit manipulation
9. **Implement FIFO read** — Two options:
   - **Option A**: Use 8-bit SPI reads and manually pack 12-bit samples from 3-byte FIFO words (the FIFO stores 2×12-bit samples per 3 bytes). This avoids the 12-bit SPI width issue.
   - **Option B**: Use Zephyr's SPI API with custom word size if the PSoC SCB driver supports it.
10. **Implement `set_fifo_limit()`** for threshold-based notification

### Phase 4: Interrupt-Driven Data Flow
11. **Wire IRQ GPIO** — configure as interrupt input, register callback
12. Implement a **work queue handler** that reads FIFO data when IRQ fires
13. Expose data via a ring buffer or callback to the application

### Phase 5: Zephyr Sensor API Integration (Optional)
14. Wrap the driver in `struct sensor_driver_api` with `sample_fetch` / `channel_get`
15. Define custom `SENSOR_CHAN_*` values for radar IF data
16. Register with `SENSOR_DEVICE_DT_INST_DEFINE`

> **Note on Phase 5**: The Zephyr sensor subsystem is designed for scalar readings (accel, temp, etc.). Radar produces large ADC frame buffers (thousands of samples). The sensor API may not be the best fit — a **custom API** with direct FIFO buffer access is more practical. The BMI270 pattern is useful for driver registration/DT/init scaffolding, but not for the data path.

### Key Decision: 12-bit FIFO Read Strategy

The official library switches SPI to 12-bit mode for FIFO reads. Zephyr's SPI API supports `spi_config.operation` with `SPI_WORD_SET(12)`, but whether the PSoC SCB driver handles it depends on the driver implementation. Recommended **Option A** (8-bit reads + manual packing) first — it's portable and simpler:

```
FIFO word = 3 bytes = 2 × 12-bit ADC samples
sample[0] = (byte[0] << 4) | (byte[1] >> 4)
sample[1] = ((byte[1] & 0x0F) << 8) | byte[2]
```

## Open items

Ordered by cost. Numbered so we can reference them by ID.

### 1. Trim the overlay (small)

Now that the binding pulls in `spi-device.yaml`, the standard SPI child
properties are inherited with defaults. The overlay
[boards/kit_pse84_ai_pse846gps2dbzc4a_m33.overlay](boards/kit_pse84_ai_pse846gps2dbzc4a_m33.overlay)
still sets:

- `duplex = <0>` — matches the default in `spi-device.yaml`, drop.
- `frame-format = <0>` — matches the default, drop.
- `spi-interframe-delay-ns = <200>` — the default of 0 means "half of SCK period", which for 25 MHz SCK is 20 ns. Keep the explicit 200 ns as a datasheet-safe margin; document why in the overlay.

Verification: pristine build must produce byte-identical `spi_config.operation` and `.word_delay` fields for the sensor instance (the two dropped properties both encode as 0 in the `.operation` OR).

### 2. Log-drop cosmetic (small)

`main.c` mixes `LOG_INF` (from the driver) and `printk` (from the app frame loop) on the same console. The log subsystem back-pressures and prints `--- N messages dropped ---` mid-line. Two clean fixes:

- Convert `main.c` to pure `LOG_INF` and bump `CONFIG_LOG_BUFFER_SIZE=2048`, **or**
- Drop `CONFIG_LOG=y`, remove the driver's `LOG_MODULE_REGISTER`, and use `printk` everywhere.

Prefer the first — the driver already has structured log module `bgt60tr13c` and losing that hurts debug.

### 3. Saturation investigation (small–medium, no code)

Every frame shows `max = 4094` (the top rail of the 12-bit ADC). Likely causes:

- `if_gain_dB = 60` in the configurator input is too high for the current test scene.
- DC offset in the IF path.
- A strong close reflector (metal on the bench).

Action: regenerate `bgt60tr13c_default_config.h` with `bgt60-configurator-cli` at `if_gain_dB = 40`, re-flash, compare. Purely a signal-processing question, not a driver bug.

### 4. Migrate to `sensor_driver_api` + RTIO streaming (large)

The current custom `struct bgt60tr13c_api` is documented as a bring-up shim in
[doc/Zephyr_Device_Drivers.md §17](../../doc/Zephyr_Device_Drivers.md#17-zephyr-sensor_driver_api-vs-a-custom-api).
Modern upstream Zephyr FIFO sensors (BMI08x, BMI270, ICM42688, BMP581) all use the standard sensor API extended with:

- `SENSOR_TRIG_FIFO_WATERMARK` from the driver's GPIO ISR — replaces our per-frame `k_sem_give`.
- `rtio_iodev` + `submit()` hook so `sensor_stream(iodev, ctx, userdata, handle)` can DMA FIFO contents into caller-supplied buffer pools.
- A `sensor_decoder_api` that unpacks the 12-bit samples into a public frame struct.

Reference implementation to mirror: [drivers/sensor/bosch/bmi08x/bmi08x_accel_stream.c](../../../../home/ubuntu/zephyrproject/zephyr/drivers/sensor/bosch/bmi08x/bmi08x_accel_stream.c).

Est. size: ~400 lines of new code + one binding extension for the RTIO iodev. Prerequisite before proposing the driver upstream.

### 5. GSR0 status checking (small–medium)

Every 32-bit SPI response from the sensor carries a 4-bit GSR0 field in bits [27:24] (`FOU_ERR`, `SPI_BURST_ERR`, `CLK_NUM_ERR`). The masks are already defined in [bgt60tr13c.h](../../modules/bgt60tr13c/drivers/bgt60tr13c/bgt60tr13c.h) but `read_reg()` masks them off and drops them; the FIFO burst read does not check them at all. Suggested change:

- Have `read_reg()` return `-EIO` on non-zero GSR0 and log which flag fired.
- Check the burst-header GSR0 in `get_fifo_data()` before trusting the payload.

This is the integrity check recommended by the Infineon reference library; without it a `CLK_NUM_ERR` (SPI misalignment) can silently corrupt a whole frame.
